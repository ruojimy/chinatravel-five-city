## 4. 什么才叫完整行程规划

完整计划必须有具体实体、逐日活动、每段移动和费用：
- 从要求的起点连续连接至终点；相邻不同地点之间有交通，返程及酒店接驳不能漏；
- 景点整个停留区间落在适用开放窗口，支持实际有证据的多时段/跨夜规则；
- 午餐、晚餐不能为了赶路消失；多日覆盖住宿后早餐、全部住宿夜数，说明餐食是否含房价，避免重复计费；
- 酒店价格与所选日期、房型、人数、房间数、床数绑定；
- 城际往返班次绑定方向、日期、站/机场、人数、座席或舱位；Duration原生小时与路线分钟显式换算；
- 总费用包含所有人、票数、房间夜数、餐饮及全部城际/市内交通，未知费用不能填0；
- TAG软偏好、天气条件和预约/库存未确认分别披露，不能用软偏好得分抵消硬约束失败。

启发式估时/模型记忆可用于候选排序，必须标明并与被认可事实隔离，不能据此通过预算、营业或交通约束。
只能生成半份计划时，保存partial_plan及明确未知，不强填数字凑官方JSON合法性；如无法送入官方checker，记录not_run及原因，不把未运行当通过。

每题保留构造调用、候选/顺序尝试、时间表、费用表、约束结果和证据引用。可以对预注册有限域搜索，但不能只试第一个候选失败就称无解。域上限、截断、未探索选择必须披露；全部已测候选失败也不自动等于全局无解。

每题分别记录，可同时出现：
- DATA：当前行程依赖的原生事实确实缺失，如适用票价、营业窗口、床数、具体班次/Duration/Cost；
- VERIFY：有候选值，但身份、精确引文语义、房型/票种范围、来源时钟或许可未闭合；
- CONTEXT：题面关键信息缺失、入口仍有实质歧义；
- ACCESS：来源暂停、挑战、限流、不可访问，注明影响哪些字段及题；
- RUNTIME_REFRESH：天气、短TTL路线/报价/库存等需要本次运行时刷新；
- ENGINEERING/ERROR：字段映射、DSL不支持、适配器未接、程序异常；
- CANDIDATE_CONSTRAINT_FAIL：某个已知候选价格太高、时间冲突；应尝试允许的其他候选；
- SEARCH_INCOMPLETE：搜索界限/未知/未覆盖域，不能称无解；
- VERIFIED_FEASIBLE_IN_SNAPSHOT / LABELLED_ESTIMATE_CONDITIONAL / INFEASIBLE_PROVEN：按实际证据和已验证的有限域证明使用。现实执行确认独立，默认false。
这些类别不是互斥百分比。许可未知不能算缺票价；“没有便宜到满足预算的对象”不能直接写为缺数据。
