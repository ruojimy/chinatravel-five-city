System Architecture and Technical Solution
System Part Technology and Data Solutions
User input
The questionnaire collects user preferences, and LLM aids in clarification. After user
confirmation, hard constraints are handed over to the checker, while soft preferences are used
for candidate ranking and evaluation of feasible solutions.
Offline test data Reuse the public request and sandbox of ChinaTravel for testing.
Online query
Networked data collection and standardization: Utilize large model networked search and map
interfaces to obtain location, traffic, and change information, extract it into a unified format
and supplement with classification and preference labels; check sources, applicable dates, and
data conflicts, save data versions for use in itinerary planning and dynamic repairs.
Program and Interface
Python is responsible for invoking large models, searching itineraries, and checking and
fixing errors; FastAPI provides interfaces, while React displays questionnaires, itineraries,
and modifies differences; SQLite stores confirmed requirements, preferences, and itinerary
versions; and maps link to view segmented routes.

Experiments
Experiment Procedure Evaluation
Initial Planning Ablation
20 verified-feasible requests. Full system vs. no check-
feedback revision vs. no questionnaire soft preferences; 
hard constraints/data/model/resources fixed. 
Feedback: valid itineraries, runtime, 
cost. Questionnaire: jointly valid cases 
scored by original profile; pass rate. 
Same independent checker.
Post-Change Revision
20 jointly feasible itineraries → 60 verified repairable 
cases: closure, delay, early departure. Compare vs. no 
modification cost; strong-model revision as reference.
Repair success rate; for joint successes: 
replacements, deletions, additions, time 
shifts. Check commuting, must-haves, 
preferences; report quality tradeoffs.
Correct No-Solution Explanation
3 types × 3 cases: confirmed conflict, feasible-but-
timeout, missing key data. Check classification, 
evidence, confirmation; no hard-constraint relaxation 
before confirmation.
Avoid “not found” as “infeasible”; no 
unauthorized changes. Report correct 
counts by type. Engineering acceptance, 
not algorithm benefit.

Risks Solution
Data is outdated or missing
Save the source, query, and effective time; missing values are not 
defaulted to zero or open all day; prompts are given when key items 
are insufficient, indicating that verification cannot be completed.
The search scale is too large Limit cities and days; cache repeated requests; set candidate and 
search budgets; retry after expanding candidates if necessary.
The checker is incorrect Test the time boundaries, transportation, budget, and lock-in 
requirements; re-examine the complete itinerary after revisions.
