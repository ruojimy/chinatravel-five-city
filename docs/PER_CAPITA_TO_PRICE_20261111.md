# 人均 → 房价：能不能换算、怎么换算（2026-11-11）

## 1. 先找“人均 + 房价”都齐全的酒店：没有找到

| 尝试 | 样本 | 同时有两项 | 说明 |
|---|---:|---:|---|
| 高德 v5/v3 酒店 `business.cost` | 29 + 25（类型检索） | **0** | 酒店 POI 基本不返回 cost |
| 百度 Place 酒店 `detail_info.price` | 6 + 26 | **0** | 精确命中酒店本体时没有 price；有值的 2 条是 SPA/茶室子场馆 |
| 全量高德扫描（240 家真实房价） | 240 | 未完成 | 代理下单请求 5–20 s，跑 25 min 仍未完，已中止；26 家定向样本与 29 家分层样本均为 0 |

已有的两条“有值”记录也证明不能用：

| 酒店 | 房费 | 百度“人均” | 命中对象 | 比值 |
|---|---:|---:|---|---:|
| 西安W酒店 | 1,116 | 872.1 | W酒店·AWAY SPA | 1.28 |
| 西安唐华华邑酒店 | 829 | 45.9 | 华邑·茗邑（茶室） | 18.1 |

结论：**高德/百度没有可用的酒店人均**，无法用我们自己的数据拟合换算系数。

## 2. 单位关系（schema 层面）

- 酒店：`price` = **每间/每晚**；`cost = price × required_rooms`；prompt：“cost per night per room”。
- 人均：**每人**的参考消费。

所以 `room_price = per_capita × 入住人数`。换算系数就是“这个人均是按几个人算的”：

| 场景 | 人均口径 | 系数 |
|---|---|---:|
| 青年旅舍/床位/太空舱 | 按床位（1 人） | **×1** |
| 普通酒店，双人房 | 按 2 人 | **×2** |
| 普通酒店，单人房，且人均按 2 人摊 | 按 2 人 | **×2**（否则就是你说的“单人房估值偏低”） |
| 普通酒店，单人房，且人均按 1 人算 | 按 1 人 | **×1** |
| 三人/家庭房 | 按 3–4 人 | ×3–×4 |

## 3. 房间结构证据（决定默认系数）

| 统计 | 数值 |
|---|---:|
| 有 `room_types` 明细的酒店 | 227 |
| 其中至少有一间 1 床房 | **225（99.1%）** |
| 只有 2 床及以上 | 2 |
| 主房型床数（1/2/3） | 148 / 33 / 2 |
| 主表 `numbed` 分布（1/2/3） | 674 / 30 / 2（多数是默认 1，不是观测） |
| 名字含“青旅/旅舍/床位/太空舱” | **9 家** |

由于 99% 的酒店都有 1 床房，而表里的 `price` 是**起步价/最低可售房型**，它大概率对应 1 床房。
如果人均是“按双人摊”的口径，那么：
- 用 **×1** 会把单床房估低约一半（正是你说的现象）；
- 用 **×2** 能对上双人房，但对单床房可能高估 0–30%（取决于单床房与双人房的真实价差）。

## 4. 建议的判定（在拿到配对样本前）

| 酒店类型 | 建议系数 | 置信 |
|---|---:|---|
| 青年旅舍/床位/太空舱（9 家） | **×1.0** | 高（按床位） |
| 普通酒店，默认（人均按双人摊） | **×2.0** | 中 |
| 已知只有单床房 / 单人入住 | **×1.6–2.0**（默认 1.8） | 低 |
| 三人/家庭房 | ×3.0 | 低 |

输出必须标 `price_status=reference_per_capita`，区间 ±25%，**不能**写成 `source_value`，也不建议直接进预算硬约束。

## 5. 工具

```bash
# 单家
python scripts/per_capita_to_room_price.py --hotel "西安W酒店" --per-capita 436
# 批量（CSV: name,per_capita）
python scripts/per_capita_to_room_price.py --batch data/candidates.csv --basis double
```

`--basis per_person` 时改用房间床数（1/2/3）作系数；`--basis double` 默认 ×2，青旅自动 ×1。

## 6. 要真正拟合系数，需要什么数据

1. **同一家酒店**同时有“人均”和“房费”的来源（大众点评/美团酒店的“人均”，或 OTA 页面里的 per-person 字段）；
2. 至少 30–50 对，按“青旅 / 单床 / 双床 / 家庭房”分层；
3. 用 `room_price / per_capita` 的分布拟合系数（中位数 + p10–p90），再用留出集验证。

在没有这批配对数据之前，**×2（普通酒店）/ ×1（青旅）** 是最符合你观察、也最保守可解释的默认规则。
