## 主流程

授权评论 → 识别评价对象与方面 → 有原文证据的TAG库。

用户query → 同一标签体系中的需求、排斥、重要程度与硬约束。

城市/日期/预算等初步筛选 → 按需求TAG召回景点 → 从实际出发点获取可用交通候选 → 景点体验与交通体验联合匹配 → 构造可行行程 → 独立核验 → 返回选择理由与证据。

匹配应在候选景点和交通方式进入行程前发挥作用，也可在完成行程后重排。只对固定的三套或十八套完整行程重排，不能证明已实现TAG驱动的候选发现。候选截断也不代表求得全局最优，必要时保留多样候选并扩大召回范围。

## 标签需要表达什么

景区评论可描述：自然/文化/摄影等主题、步行负担、台阶、拥挤、排队、遮阴、休息设施、雨天体验等。交通评论可描述：具体进出路线、方式、接驳步行、换乘、候车、拥挤、上下客点、坡道/楼梯等。属性与体验分开；存在一班公交不等于交通体验好。

共享的标签词典不要求两侧语义完全相同：评论描述观察到的体验，query描述希望获得或避免的体验。使用同一方面及可比较取值进行匹配：

|方面|评论侧示例|query侧示例|匹配关系|
|---|---|---|---|
|自然风光|nature=true|偏好nature=true|正向支持|
|步行负担|walking_burden=high|希望walking_burden=low|冲突，不能因都提“步行”而加分|
|台阶|stairs=many|不爬台阶|排斥；是否硬约束取决于用户表述|
|排队|queue=long、节假日|尽量少排队|情境一致时负向支持|

上表是设计示例，不是新采集的真实景区证据。

建议需求项记录aspect、desired_value、relation（prefer/avoid/max/min）、strength（hard/soft）、weight、user_excerpt、confidence。评论项记录target_type、target_id、aspect、observed_value、context、source、review_id、excerpt、observed_at、confidence和冲突统计。

“尽量少走路”是软偏好；“每天步行不超过1公里”有明确硬上限。不从“带父母”自动推断行动能力，不从“有预算”自动推断极度价格敏感。否定、转折、条件与指代都需要在抽取时处理。

## 交通标签的对象范围

对象至少分为：景区本体、通往/离开景区的具体路线或接驳段、具体交通服务、景区内交通。交通记录须尽可能带起终点、方向、方式和时间情境。同一景点从不同车站或酒店出发，适用的交通记录可能不同；不能给所有地铁或公交一个通用好坏标签。

若评论仅说“坐地铁下来还要走很久”，没有站点/出口信息，可存为该景区的弱交通提示，路线身份标unknown，不能伪造具体路段。规划时结合可验证路线数据确认是否适用于本次路径。

先检查硬约束和路线可行性，再比较景区标签收益、交通标签冲突与证据可信度。缺评论显示unknown/覆盖不足；不能直接当差评，也不能让完全无证据的候选凭零惩罚胜出后被说成匹配最佳。需要展示哪些需求得到支持、哪些未知，并在关键要求无法验证时澄清或保守处理。

## 当前实现与目标的差距（本地核对）

|环节|现状|下一步|
|---|---|---|
|query抽取|preference.py关键词画像，已有来源/置信度与硬约束候选|处理否定、方向和条件；对齐评论方面；区分用户显式说法与推断|
|评论TAG|visitor_tags.py已有规则与原文提及|核验方面-取值-对象关系，不能将交通方式的出现直接当正向质量|
|TAG存储|tagstore.py主键与索引以local_poi_id为中心|增加交通对象与路径上下文，不把路线评论混入景区本体|
|候选生成|planner.py主要按距离/价格/时长及prefer_mode选候选|接入景点TAG召回和交通候选匹配，避免只在生成后重排|
|完整行程排序|rerank.py的rank_plans已存在|保留作组合级核验后的重排，不把它当作前置TAG检索已实现的证据|
|真实体验覆盖|既有检查点的授权游客语料仅覆盖一个景区，未接入目标十城|先选有授权、可匹配的少量景区与交通建立端到端实测；不足处保持未知|

本轮两个确定性复现见results/p9_tag_matching_alignment/implementation_gap_checks.json：自然语言“不喜欢爬山、不想拍照，可以排队”被提取为nature/photography正兴趣与低排队容忍；合成评论“There is a shuttle bus, but we waited forty minutes.”被提取为reachability=high。它们是诊断夹具，不是真实游客评论，也不是总体准确率。

## 更贴近此目标的验证

1. 评论抽取：评价者只看短原文与提取TAG，判断对象、方面、值、否定/转折是否忠实，不需要去过该景区。该标注回答“原文是否支持”，不是“评论在真实世界是否正确”。
2. query抽取：评价者只看用户原话和需求TAG，检查有无遗漏、反向理解或臆测。
3. 匹配：使用独立标注的小样本需求—证据对，核对召回、冲突识别、关键需求覆盖与未知处理。用明确标注的合成反例做校准，不能把系统自身分数当标签。
4. 组合规划：相同候选空间比较是否接入景点TAG、是否进一步接入交通TAG；独立checker评硬约束，另报行程级匹配证据与代价。未完成实测前不声称改进。
5. 少量完整行程可接受度或真实采纳反馈作为补充。目标先落在TAG抽取忠实度、需求理解和候选匹配上，不要求人先替所有陌生城市整条行程打分。
