# P34 规划器详解（ConstraintPlannerV2）

**代码**：`src/shorttrip/planner_v2.py`（483 行）＋ `planner.py`（种子构造，478 行）＋ `scheduler.py`（重建，167 行）＋ `checker.py`（裁决，144 行）
**运行器**：`scripts/p34_run_v2.py`　**汇总**：`scripts/p34_aggregate.py`
**成绩**：三关全过 easy 48.7% / medium 46.0% / human 70.8%（300 / 150 / 154）
**代价**：单题 0.41 / 0.86 / 0.70 s，平均 5.8 / 15.3 / 9.6 次评估，0 LLM token

---

## 0. 一页速览

| 问题 | 回答 |
| --- | --- |
| 它是什么 | 一个**纯规则、无 LLM、完全确定性**的行程规划器：读 query 里的可执行 DSL，产出官方 schema 的 plan，并用**未修改的官方 checker** 自证 |
| 怎么保证不"自嗨" | 所有接受/拒绝都由 `check_plan`（官方 schema + commonsense + hard DSL）判定；规划器没有自己的评分哲学 |
| 为什么比 P33 强 | 不是调参，而是**补动作**：把失败约束族逐个映射成候选生成阶段（8 个），并给"远处酒店被静默丢弃"加了越界变体 |
| 为什么这么快 | 搜索空间被地理预筛（9–12 km）压到几十个候选；每题只做 6–15 次「重建 + 全检」 |
| 最大短板 | 语义理解（只认 DSL，不认自然语言）、交通方式覆盖（不会"故意打一次车"）、餐段与营业时间的联合校验、全局重排 |

---

## 1. 设计原则

1. **确定性优先**：不用随机数、不用 LLM；同一 query 必得同一 plan（可复现、可归因）。
2. **checker-in-the-loop**：判断"改得好不好"的唯一标准是官方 checker 的返回，不引入自建评分。
3. **重建而非打补丁**：任何内容级编辑之后，由 `schedule()` **重算整条时间链**，保证每段接驳都与 `goto` 的价格/时长一致——这样"改完看着对、时间对不上"的失败模式被结构性排除。
4. **动作库即能力**：P33 的诊断是"失败按约束族整组出现"，因此每加一个族的动作，分数就阶跃一次（+18.7 / +28.0 / +24.7 pt），调参只值 1–2 pt。

## 2. 三个数据结构

### 2.1 输入 `query`

```
uid, tag, start_city, target_city, days, people_number,
limit_rooms, limits_room_type,
hard_logic_py: [str],     # 可执行 DSL 约束（官方 IR）
nature_language / nature_language_en   # 规划器不读
```

**关键**：规划器**只读 `hard_logic_py`**，不解析自然语言。这是它快且稳的原因，也是它无法处理软约束和同义表达的原因。

### 2.2 输出 `plan`（官方 schema）

```json
{"people_number": 2, "start_city": "南京", "target_city": "武汉",
 "itinerary": [{"day": 1, "activities": [
    {"start": "南京南站", "end": "武汉站", "start_time": "06:55", "end_time": "09:25",
     "price": 296.86, "cost": 593.72, "tickets": 2, "type": "train", "TrainID": "G3591", "transports": []},
    {"start": "...", "end": "...", "_from": "景点", "type": "attraction", "position": "晴川阁",
     "start_time": "10:11", "end_time": "12:11", "price": 0.0, "tickets": 2,
     "transports": [{"mode": "metro", "tickets": 2, "cost": 3, "distance": 4.1, ...}]}
 ]}]}
```

活动类型：`train` / `airplane`（城际）、`attraction`、`breakfast|lunch|dinner`、`accommodation`；每段市内接驳挂在 `transports` 里（`walk` / `metro` / `taxi`），由 `goto` 决定。

### 2.3 自检 `CheckReport`

```python
schema_ok: bool
commonsense_ok: bool
commonsense_violations: list[str]     # 违规列名
hard_results: list[bool]              # 与 hard_logic_py 一一对应
hard_codes: list[str]
# 派生：hard_ok = all(...) / hard_pass_count = sum(...) / all_ok = 三关全过
```

论文口径对照：`schema`→DR（口径不同，仅"交付合法性"）、`commonsense`→EPR-Mac、`hard`→LPR-Mac、三关全过→**FPR**。

## 3. 端到端流水线

```
query
 │
 ├─① SkeletonPlanner.build()          # 城际组合枚举 + 地理感知候选 + 逐日填充
 │      └─ 最多 6 个 (go,back) 组合，逐个构造 + check_plan
 │
 ├─② RepairEngine.repair(..., room_type_fix=True)   # P33 的 9 阶段旧修复（基线）
 │      └─ 只在 hard 不降时接受（取旧版净收益）
 │
 ├─③ parse_spec(query)                # 读 DSL（含 result=(...) 里的类型集合）
 │
 ├─④ 八个定向阶段（按顺序，逐阶段评估）
 │       intercity → hotel → must_attraction → must_restaurant
 │       → attraction_type → restaurant_type → per_meal → budget
 │
 └─⑤ 裁决：每次候选都 schedule() 重排 + check_plan() 全检
        接受条件：score=(hard_pass, commonsense, schema) 严格变好，且评估数 < 60
```

伪代码（简化）：

```python
def plan(query):
    seed = SkeletonPlanner(env).build(query)          # ①
    plan, report = better_of(seed, legacy_repair(seed))  # ②
    if report.all_ok: return plan
    spec = parse_spec(query)                          # ③
    state = extract_content(plan)                     # (go, back, hotel, content)
    for stage in STAGES:                              # ④
        for candidate_state in stage(query, spec, state):
            new_plan = schedule(env, query, **candidate_state)   # ⑤ 重建时间链
            new_report = check_plan(query, new_plan)
            if score(new_report) > score(best_report):
                plan, report, state = new_plan, new_report, candidate_state
    return plan, report
```

## 4. 第 0 层：种子构造器（`SkeletonPlanner`）

### 4.1 城际组合枚举

- 去程：`start_city → target_city`，只取 06:00–13:00 出发的班次，按出发时间+票价排序，取前 5。
- 返程：反向，按**最晚出发**排序取前 5（给最后一天留时间）。
- 组合成 `pairs`，最多试 `max_combos=6` 个；1 天行程额外要求「去程到达 ↔ 返程出发 ≥ 150 分钟」。
- 任一组合构造成功且 `schema_ok and commonsense_ok` 就**提前返回**（注意：此时还不要求 hard 全过，hard 交给后面几层）。

### 4.2 地理感知候选池

- 用 `poi_search` 的经纬度算 haversine 距离；
- 末天候选半径 **9 km**（要赶车），非末天 **12 km**；餐厅固定 8 km；
- `_ranked()` 按 `order_by`（distance / price / duration）排序 —— 这个开关原本是为"多偏好候选池"准备的，默认 distance。

**作用**：把 tens of thousands 行沙盒压到每类几十个候选，是"亚秒级"的根本原因。

### 4.3 逐日填充状态机（`_fill_day`）

最多 8 轮，每轮依次判断：

| 时间窗 | 动作 |
| --- | --- |
| 11:00–14:00 且未午餐 | 插入 `lunch`（60 min） |
| 17:00–20:00 且未晚餐 | 插入 `dinner`（60 min） |
| 其它且景点数 < 3 | 插入一个 `attraction`（时长 = `recommendmintime`，最少 45 min） |

每插一项前都要过 `affordable()`：末天用「当前位置 → 车站」的真实接驳 × **1.3 滑差** 反推是否还赶得上返程（`deadline = 返程开车 - 25 min`）。

### 4.4 末天可达性与酒店

- `close_with_station()` 若连车站都到不了，直接判定该组合不可行（`last_reason` 记录原因）；
- 酒店：取「当天最后一个位置」可达的最便宜候选；房间数 `ceil(people / numbed)`；
- 只有非末天住酒店，末天直接返程。

## 5. 第 1 层：旧修复基线（为什么还留着）

`RepairEngine` 的 9 个阶段（names / types / forbidden / intercity / go_time / return_time / counts / room_type / budget）在 P33 上把 easy 从 30.0% 拉到 30.0%（无变化），但中等难度上靠 `room_type` 修复把全过从 18% 拉到 28%。

V2 的策略是**不重写它，先吃它的收益**：seed 之后跑一遍旧引擎（`max_evaluations=25`、`room_type_fix=True`），只在 hard 通过数不降时接受。这样 V2 的每个 +pt 都是**在旧版之上的净增量**，也避免了"新版本某些题变差"的回归。

---

## 6. 第 2 层：约束解析（`parse_spec`）

### 6.1 旧解析器漏了什么

`repair.parse_requirements` 用正则扫**赋值语句**，但 ChinaTravel 的类型集合约束长这样：

```python
accommodation_type_set=set()
for activity in allactivities(plan):
    if activity_type(activity) == 'accommodation':
        accommodation_type_set.add(accommodation_type(activity, target_city(plan)))
result=({'儿童乐园'} <= accommodation_type_set)     # ← 集合在这里！
```

于是 `attraction_type_set` / `restaurant_type_set` / `accommodation_type_set` **四条约束族全程没被读到**——P33 里这三族合计 30+21+4 题失败，根因就在这里。

### 6.2 `parse_spec` 的规则

| 目标 | 提取方式 |
| --- | --- |
| 类型集合 | 先看约束里出现哪个 `*_type_set` 变量，再从 `result=` 后的引号里取集合 |
| 必去名称 | `result=(... '名字' in attraction_name_set)` 形式 |
| 城际 / 市内方式集合 | `intercity_transport_set` / `innercity_transport_set` 的 `result=` 集合 |
| 预算 | `total_cost|food_cost|hotel_cost|attraction_cost|transportation_cost|food_cost/food_count/people_count <= N` |
| 房型 / 票数 / 房数 | `room_type|tickets|room_count == N` |
| 出发时间窗 | DSL 里成对出现的 `HH:MM`（仅在 intercity 约束内） |

产物是 `Spec` 对象，字段命名与旧 `Requirements` 兼容，便于两个解析器共存。

## 7. 第 3 层：八个定向阶段

每个阶段都是**纯函数**：输入 `(query, spec, state)`，输出若干 `(candidate_state, label)`；不接受副作用，不自己判分。

| # | 阶段 | 针对的约束族 | 候选生成 |
| --- | --- | --- | --- |
| 1 | `intercity` | 城际方式集合（含 `airplane`） | 对集合中每个模式重建 go/back 两条 leg |
| 2 | `hotel` | 酒店设施 / 指定酒店 / 房型 | 按 `featurehoteltype`、`numbed`、名称过滤后按价排序，最多 5+2 个；每个再配一个"删末位景点"的越界变体 |
| 3 | `must_attraction` | 必去景点名称 | 全位置插入 + 与当日非必去景点互换（上限 24 个候选） |
| 4 | `must_restaurant` | 必去餐厅名称 | 按营业时间选餐段；优先**同餐段替换**，其次跨餐段替换，最后才追加（上限 20） |
| 5 | `attraction_type` | 景点类型集合 | 用同类型最便宜的 4 个候选替换不匹配项（上限 20） |
| 6 | `restaurant_type` | 菜系集合 | 同上，按 `cuisine` |
| 7 | `per_meal` | 人均餐费上限 | 换成最便宜的 5 家餐馆 |
| 8 | `budget` | 总/分类预算 | 换更便宜酒店、删非必去景点 |

### 7.1 阶段 2 的"越界变体"（本轮最关键的三行）

换到远处酒店后，`schedule()` 会因"当日回不到酒店"**静默跳过住宿活动**：

```python
elif hotel_row is not None:
    if not builder.add_hotel(hotel_row, rooms):
        return None
```

于是 `accommodation_type_set` 仍然为空，看起来像"换酒店没生效"，实际是"酒店根本没排进计划"。V2 为每个候选酒店额外提供一个「删掉末日最后一个非必去景点」的变体，腾出时间让酒店排得进去。失败最密的 20 题窗口由此从 **0/20 → 12/20**。

### 7.2 阶段 4 的餐段规则

```python
def _meal_kind(city, name):
    row = lookup_row(restaurant_table(city), name)
    open_min, close_min = _hhmm(row['opentime']) or 0, _hhmm(row['endtime']) or 24*60
    # 与 breakfast(7-10) / lunch(11-14) / dinner(17-21) 求重叠，取最大者
```

南京"小酒小肉烤串店"16:30 才开门，按午饭排会被调度丢弃——这是 P33 里 easy 30 题必挂的原因；V2 会把它排到晚餐段。

## 8. 裁决层：怎么判断"改好了"

```python
def score(rep):
    return (rep.hard_pass_count, int(rep.commonsense_ok), int(rep.schema_ok), cost)
```

- **字典序**：先比 hard 通过条数，再比 commonsense，再比 schema；
- 第四个分量（成本）目前**不生效**——`CheckReport` 没有 `total_cost` 字段，`getattr` 取到 `None`，恒为 0。它只是给"同分时偏好便宜方案"预留的位置，不要当成已实现的能力；
- **预算**：每题最多 `max_evaluations=60` 次「`schedule` + `check_plan`」，实测平均只用 5.8 / 15.3 / 9.6 次；
- **早停**：一旦某次评估 `all_ok` 为真，立即返回，不再继续花钱。

## 9. 复杂度与实测性能

| split | 题数 | 单题均值 | 中位数 | p95 | 总耗时 | 平均评估次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| easy | 300 | 0.41 s | 0.30 s | 0.95 s | 122.8 s | 5.8 |
| medium | 150 | 0.86 s | 0.72 s | 2.22 s | 128.9 s | 15.3 |
| human | 154 | 0.70 s | 0.39 s | 2.29 s | 107.1 s | 9.6 |
| *P33 旧版对照* | — | 0.21 / 0.32 / 0.37 s | — | — | 63.6 / 47.5 / 57.5 s | — |

**为什么是亚秒级**：

1. 候选池被地理预筛到几十个，`_ranked` 只是排序不是搜索；
2. 大多数题在种子或旧修复阶段就 `all_ok`，直接返回（评估数 0）；
3. 需要 V2 介入的题平均只跑十几次「重建 + 全检」，每次重建是 O(天数 × 活动数) 的时间链拼接；
4. 没有回溯树、没有节点展开——这是与官方 RuleNeSy（197,618 节点 / 300 s 打满）最本质的差别。

**代价**：比 P33 慢 1.9–2.7 倍（更多候选与重建），换来 +18.7 / +28.0 / +24.7 pt 的全过率。604 题跑完约 6 分钟。

## 10. 能力边界矩阵

| 约束族 | P34 能否处理 | 机制 / 原因 |
| --- | --- | --- |
| 天数 / 人数 / 票数 | ✅ | seed 直接构造；`_fix_numeric` 兜底 |
| 城际方式集合 | ✅（含 airplane） | 阶段 1；需写 `FlightID` 而非 `TrainID` |
| 酒店设施 / 房型 / 指定酒店 | ✅ | 阶段 2（含越界变体） |
| 必去景点 / 餐厅 | ✅（多数） | 阶段 3/4（插入 + 互换 + 餐段选择） |
| 景点类型 / 菜系集合 | ✅（集合可枚举时） | 阶段 5/6 |
| 预算（总 / 分类 / 人均餐费） | 🟡 | 阶段 7/8 只会"换便宜"，不做全局取舍 |
| 市内交通方式集合（如"必须打一次车"） | ❌ | 无"强制交通方式"动作；`best_mode` 永远选最优 |
| 时序类（第 k 天必须几点到某地） | 🟡 部分 | 只有末天 deadline 与出发窗；无跨天重排 |
| 顺序类（"先 A 后 B"） | ❌ | seed 顺序固定，不搜索顺序 |
| 软约束 / 偏好 | ❌ | 不读自然语言，也无偏好评分（见 §12.3） |

**残余失败证据**（P34）：easy 最大失败列 `logic_py_3` 95 次（多为市内交通方式）、medium `logic_py_6/7/8` 30/21/20 次、human `logic_py_0/1` 21/11 次（必去名称 + 类型集合同时要求）。commonsense 残余以"用餐时间"为主（22/15/9 题）。

## 11. 与其它规划器的定位

| 规划器 | 语义理解 | 搜索 | 事实正确性 | 时间/题 | 三关全过（easy） |
| --- | --- | --- | --- | ---: | ---: |
| **P34 V2** | 正则读 DSL | 定向构造 + 局部候选 | 由 `schedule`/`goto` 保证 | **0.41 s** | **48.7%** |
| P33 旧 | 正则（漏类型集合） | 9 阶段盲改 | 同上 | 0.21 s | 30.0% |
| 官方 RuleNeSy | 规则翻译 | DFS + 回溯 | 同上 | 300 s 打满（3 天题） | 未跑全量 |
| NeSy × flash | **LLM 翻译** | DFS + 回溯 | 同上 | ≈186 s | 8/8（8 题切片） |
| 纯 LLM（Act） | LLM 全程 | 无（直接生成） | **自编数据** | ≈140 s | 0/8（8 题切片） |

一句话：**P34 把"理解"交给 DSL，把"正确性"交给 checker，自己只负责"在可行域里高效找点"**——因此在硬约束明确时极快极稳，在需要语义等价或全局重排时无能为力。

## 12. 已知缺陷与改进优先级

| 优先级 | 缺陷 | 影响面 | 改法 |
| --- | --- | --- | --- |
| P0 | 无"强制交通方式"动作 | easy 23 / medium 8 题 | 新增阶段：把一段接驳改成目标模式，重算价格与时长 |
| P0 | 餐段与营业时间未联合校验 | commonsense 22/15/9 题 | 阶段 4 加一层"排完回看时间是否落在餐段内" |
| P1 | 必去名称 + 类型集合互相挤占 | human 21+11 题 | 联合动作：一次替换同时满足两条（而不是逐条修） |
| P1 | 顺序不可搜索 | 若干"压线"题 | 天的顺序做局部交换（模拟退火/枚举前 k） |
| P2 | 预算只做"换便宜" | medium 21 / human 19 题 | 加"删点/换点"与预算的影子价格 |
| P2 | 成本分量未接通 | 无（预留） | 给 `CheckReport` 加 `total_cost`，或在 score 里传 |

## 13. 如何新增一个阶段（模板）

1. **定位失败族**：从 `logical_py.csv` 的失败列分布里找整组失败（不是零散失败）；
2. **确认可控变量**：这个族对应的是 `content` 里的哪一项（景点/餐厅/酒店/leg）；
3. **写 `_stage_xxx(query, spec, state)`**：返回 `[(candidate_state, label)]`，**不要**在里面判分；
4. **注册到 `stages` 元组**：顺序放在"依赖更少"的阶段之后（例如类型替换放在必去名称之后，避免把必去项换掉）；
5. **跑 20 题窗口验证**：用一个失败密集的 `--offset` 窗口对比 hard 通过数，确认是阶跃而不是噪声。

代码骨架：

```python
def _stage_xxx(self, query, spec, state):
    out = []
    for day, items in state["content"].items():
        for index, (kind, name) in enumerate(items):
            if 不满足目标条件(name):
                for replacement in 候选池(name):
                    candidate = self._copy(state)
                    candidate["content"][day][index] = (kind, replacement)
                    out.append((candidate, f"{name}->{replacement} d{day}"))
    return out[:20]
```
